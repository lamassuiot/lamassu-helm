# Migration guide from 3.8.0 to 4.0.0

Version 4.0.0 is a security-hardening release: every workload now runs as a
numeric non-root user (`65532:65532` by default) and every chart-managed
resource name became release-scoped (via a new `lamassu.fullname` helper),
instead of the fixed, unscoped names used in 3.8.0 (`kms`, `va`, `ca`, ...).

> [!WARNING]
> The resource-naming change is **not** a cosmetic rename. For the two
> StatefulSets that use a local PVC — **KMS** (`services.kms.cryptoEngines`
> with a `filesystem` engine) and **VA** (`services.va.fileStore.type: local`)
> — Kubernetes derives the auto-generated PVC name from the StatefulSet's pod
> name (`<volumeClaimTemplate>-<pod-name>`). Renaming the StatefulSet from
> `kms`/`va` to `<chart fullname>-kms`/`<chart fullname>-va` means
> `helm upgrade` does **not** reuse your existing PVCs — it silently binds
> brand-new, empty ones.
> Your existing KMS key material and VA CRLs are not deleted, but the
> upgraded pods will fail to find them (`no such file or directory` /
> `code=NotFound`) until you move the data across yourself. Deployments and
> Services (CA, UI, Alerts, etc.) rename the same way but are stateless, so
> they just get recreated with no data-loss risk — only KMS and VA need the
> manual step below.

**Upgrade order:** record the old PVC names, run `helm upgrade` to 4.0.0,
then copy the data into the new PVCs. The copy commands below **must run after
the upgrade**, because the destination StatefulSets and PVCs do not exist
before it. Verify KMS and VA before deleting the old PVCs.

## Before you upgrade: record the old PVCs

Do not delete the pre-upgrade PVCs until you've verified the new ones work.
`helm upgrade` does not touch or remove them — they become orphaned, not
destroyed — so this step is about *knowing their names before they're no
longer referenced by anything*, not about creating a new backup.

Set the namespace and Helm release name once per shell, adjusting the values
to your installation:

```bash
export NAMESPACE=lamassu   # your 3.8.0 install's namespace
export RELEASE=lamassu     # your helm release name
```

```bash
kubectl get pvc -n $NAMESPACE -l app.kubernetes.io/instance=$RELEASE
# or, on a 3.8.0 install, just look for the unscoped names directly:
kubectl get pvc -n $NAMESPACE golang-engine-storage-kms-0 local-crl-file-storage-va-0
```

## After you upgrade: migrate the PVC data

After `helm upgrade` to 4.0.0 has run, the new (empty) PVCs exist
alongside the old ones. Each service stores its data independently, so
migrate each one separately and **only the ones you actually use**:

| Service | Migrate if you ever used | Old PVC |
| --- | --- | --- |
| KMS | a `filesystem` engine in `services.kms.cryptoEngines` | `golang-engine-storage-kms-0` |
| VA | `services.va.fileStore.type: local` | `local-crl-file-storage-va-0` |

> [!NOTE]
> Skip a subsection if its condition doesn't apply (for example, KMS backed
> by an external engine has no KMS StatefulSet and no KMS PVC). Skip this
> whole section if you're doing a fresh install or neither condition applies.

The new StatefulSet names depend on the release name and any `nameOverride`
or `fullnameOverride`, and the new PVC name is
`<volumeClaimTemplate>-<StatefulSet name>-0`. For example, a release named
`prod` with the default chart name has `prod-lamassu-kms` and
`prod-lamassu-va`, not `prod-kms` and `prod-va`.

### Migrate KMS data

```bash
KMS_STS=$(kubectl get statefulset -n "$NAMESPACE" \
  -l "app.kubernetes.io/instance=$RELEASE,app.kubernetes.io/component=kms" \
  -o jsonpath='{.items[0].metadata.name}')
KMS_PVC="golang-engine-storage-${KMS_STS}-0"
printf 'KMS StatefulSet: %s; new PVC: %s\n' "$KMS_STS" "$KMS_PVC"

kubectl get pvc -n "$NAMESPACE" golang-engine-storage-kms-0 "$KMS_PVC"
```

Confirm the StatefulSet name is present and both PVCs exist before
continuing. Scale the KMS StatefulSet down so nothing is writing to either
volume while you copy, then run a short-lived pod that mounts both PVCs:

```bash
kubectl scale statefulset -n "$NAMESPACE" "$KMS_STS" --replicas=0

cat <<MANIFEST | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pvc-migrate-kms
  namespace: $NAMESPACE
spec:
  restartPolicy: Never
  containers:
    - name: migrate
      image: docker.io/library/alpine:3.20
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - {name: old, mountPath: /old}
        - {name: new, mountPath: /new}
  volumes:
    - {name: old, persistentVolumeClaim: {claimName: golang-engine-storage-kms-0}}
    - {name: new, persistentVolumeClaim: {claimName: $KMS_PVC}}
MANIFEST
kubectl wait -n "$NAMESPACE" --for=condition=Ready pod/pvc-migrate-kms --timeout=60s
```

Inspect before you write anything, so you don't clobber data the new pod
may already have written on its own:

```bash
kubectl exec -n "$NAMESPACE" pvc-migrate-kms -- sh -c 'find /new -type f'
```

If that comes back empty (the common case — a StatefulSet's own pod never
gets far enough to write anything when its dependent data is missing), copy
the old data across and align ownership with the new non-root identity:

```bash
kubectl exec -n "$NAMESPACE" pvc-migrate-kms -- sh -c '
  cp -a /old/. /new/ &&
  chown -R 65532:65532 /new
'
```

Clean up and scale back up:

```bash
kubectl delete pod -n "$NAMESPACE" pvc-migrate-kms
kubectl scale statefulset -n "$NAMESPACE" "$KMS_STS" --replicas=1
```

### Migrate VA data

```bash
VA_STS=$(kubectl get statefulset -n "$NAMESPACE" \
  -l "app.kubernetes.io/instance=$RELEASE,app.kubernetes.io/component=va" \
  -o jsonpath='{.items[0].metadata.name}')
VA_PVC="local-crl-file-storage-${VA_STS}-0"
printf 'VA StatefulSet: %s; new PVC: %s\n' "$VA_STS" "$VA_PVC"

kubectl get pvc -n "$NAMESPACE" local-crl-file-storage-va-0 "$VA_PVC"
```

Confirm the StatefulSet name is present and both PVCs exist before
continuing. Scale the VA StatefulSet down, then run a short-lived pod that
mounts both PVCs:

```bash
kubectl scale statefulset -n "$NAMESPACE" "$VA_STS" --replicas=0

cat <<MANIFEST | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pvc-migrate-va
  namespace: $NAMESPACE
spec:
  restartPolicy: Never
  containers:
    - name: migrate
      image: docker.io/library/alpine:3.20
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - {name: old, mountPath: /old}
        - {name: new, mountPath: /new}
  volumes:
    - {name: old, persistentVolumeClaim: {claimName: local-crl-file-storage-va-0}}
    - {name: new, persistentVolumeClaim: {claimName: $VA_PVC}}
MANIFEST
kubectl wait -n "$NAMESPACE" --for=condition=Ready pod/pvc-migrate-va --timeout=60s
```

Inspect, then copy and fix ownership:

```bash
kubectl exec -n "$NAMESPACE" pvc-migrate-va -- sh -c 'find /new -type f'
```

If that comes back empty, copy:

```bash
kubectl exec -n "$NAMESPACE" pvc-migrate-va -- sh -c '
  cp -a /old/. /new/ &&
  chown -R 65532:65532 /new
'
```

Clean up and scale back up:

```bash
kubectl delete pod -n "$NAMESPACE" pvc-migrate-va
kubectl scale statefulset -n "$NAMESPACE" "$VA_STS" --replicas=1
```

> [!IMPORTANT]
> On 3.8.0, `serviceDefaults.securityContext` was `{}` — every container ran
> as whatever UID its image happened to declare (root, or a mutable tag's
> then-current `USER`, which is not a stable guarantee — see `SECURITY.md`).
> The `chown -R 65532:65532` step is required even if your old files already
> look non-root-owned, since 4.0.0 pins the identity to exactly `65532:65532`
> and does not fall back to whatever the image declares.

### Verify and clean up

Verify each migrated service comes up without `NotFound`/`no such file or
directory` errors in its logs, and, for VA, that a previously-issued CRL is
servable again (`GET /crl/<ca-ski>`). Once you've confirmed the new PVCs are
good, delete the orphaned old ones for the services you migrated to reclaim
storage:

```bash
kubectl delete pvc -n "$NAMESPACE" golang-engine-storage-kms-0   # KMS, if migrated
kubectl delete pvc -n "$NAMESPACE" local-crl-file-storage-va-0   # VA, if migrated
```

## Update Helm values.yaml (aka lamassu.yaml)

### NEW services.authz

3.8.0 had no `authz` service at all — every route was open to anyone with a
valid token. 4.0.0 adds it as a required first-class service (fine-grained,
entity-level authorization), which means a 3.8.0 values file has nothing to
migrate *from*: you must add its configuration by hand, or the upgrade comes
up with authorization wired in but nothing configured to back it.

Add:

```yaml
services:
  authz:
    credentials:
      pki:
        database: pki
      authz:
        database: authz
```

> [!NOTE]
> `services.authz.credentials.<schema>` only reads the `database` field —
> `hostname`/`port`/`username`/`password` are accepted (nothing rejects
> them) but ignored; every schema's Postgres connection always uses the
> chart's single global `postgres.hostname`/`port`/`username`/`password`.
> There's no per-schema credential support yet, so there's no need to repeat
> those four fields under `pki`/`authz` — `database` is the only field that
> does anything.

The two keys are not interchangeable:
- `authz` is authz's own storage for principals, grants and policies
  (`services.authz.database`, already `authz` by default — this entry just
  gives the authorization *engine* itself a connection to that same
  database, distinct from the service's own `authz_db` connection).
- `pki` is a separate database the authorization engine queries when
  evaluating policies against entities (CAs, certificates, devices, DMSs,
  KMS keys, VA roles — see `connectors/authz/pki.json` in the `lamassuiot`
  repo for the full entity list).

> [!WARNING]
> The `pki` database is **not** one of the databases the chart already
> creates and migrates (`migrations.db.databases` only covers `alerts`,
> `ca`, `va`, `devicemanager`, `dmsmanager`, `kms`). Provisioning it is on
> you, outside this chart, before `authz` can start cleanly.

Finally, confirm `services.authz.bootstrap` (defaulted in `values.yaml`)
matches how your OIDC provider assigns the `pki-admin` realm role. Without a
principal matching that bootstrap rule, a fresh 4.0.0 authz install comes up
with **no one able to administer the PKI** — there's no implicit superuser.

### RENAMED toolbox → connectivityTest

The `helm test` connectivity-check hook no longer uses a chart-owned
`ghcr.io/lamassuiot/toolbox` image; it now uses the upstream-maintained
`curlimages/curl` image, pinned by digest. If you had a `toolbox:` override
in your values file, rename it:

**OLD (3.8.0):**
```yaml
toolbox:
  image: ghcr.io/lamassuiot/toolbox:dev
```

**NEW (4.0.0):**
```yaml
connectivityTest:
  image: curlimages/curl@sha256:...
```

> [!NOTE]
> `values.schema.json` now rejects unknown top-level keys, so a leftover
> `toolbox:` key will fail `helm lint`/`helm upgrade` outright rather than
> being silently ignored.

### REMOVED per-service `runAsGroup`/`runAsUser` identity overrides

`services.kms.securityContext.runAsGroup: 0` and
`services.authz.securityContext.{runAsUser,runAsGroup}: 999` were removed.
Both services (and their images) now use the chart-wide `65532:65532`
default directly; KMS's PVC and PKCS#11-socket group access is instead
handled by `fsGroup: 65532` set automatically on the pod. If you had copied
either override into your own values file to match a previously-declared
image identity, remove it — the current images already declare `65532`.
